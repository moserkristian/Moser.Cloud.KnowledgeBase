How a question flows through this app

RAG (retrieval-augmented generation) is not a single box. A policy file is loaded, sliced, turned into numbers, stored, then later matched to a question so the model can answer from those slices only. Terms live on /legend.

Play / next step below. Allow / Deny / NeedsHuman changes the sample question. The packet is a real file, then a chunk, then embedding numbers.

KrokČo to je jednou vetouAnalógia
Ingest Pri štarte Web sa politiky načítajú do systému. Ešte sa nikto nepýta. Niečo skopíruješ do kartotéky.
Chunk Dlhý .md sa nareže na odstavce. Celý šanón nestrčíš do vrecka; vystrihneš lístok „14 dní“.
Embed Lístok sa premení na kopku čísel („smer významu“). Lístok dostane GPS súradnice.
Index Tie lístky + čísla sa uložia. Toto je vector store. Zásuvka s kartičkami. Teraz v RAM, neskôr pgvector.
Retrieve Otázka dostane tiež GPS a vytiahnu sa najbližšie lístky. „Daj mi 5 kariet najbližšie k tejto otázke.“
Generate LLM napíše vetu len z tých kariet. Intern môže použiť len to, čo leží na stole.
Policy C# po modeli. Vie povedať Deny, aj keď intern povedal áno. Strážnik pri dverách. Model ho nevie prepísať.

Dva časy: horný rad (ingest) sa stane raz pri štarte. Dolný rad (ask) pri každej otázke.

Stub nie je LLM. Je to záslepka dvoch zásuviek.

Web potrebuje zapojiť dve veci: text → čísla a napíš vetu. Tie rozhrania (IEmbeddingGenerator, IChatClient) musia mať nejakú implementáciu, inak sa proces nespustí. Keď Ollama nebeží, factory tam nestrčí llama — strčí dve C# triedy, aby DI nespadlo. RAG rúra (súbor → chunk → index → search → Policy) beží aj tak. Chýba len mozog.

Embed Spočíta výskyty slov do 64 čísel (taška na nákup: koľkokrát „PTO“, „days“…). Súradnice významu. „holiday“ a „PTO“ môžu byť blízko.

Otázka How many PTO days do US employees get?
Čo vylezie „US full-time employees accrue 20 PTO days per year.“ — skopírované z pto-us.md. Napr. „US employees get 20 PTO days a year (pto-us.md).“ — napísané modelom.
„holiday allowance in America“ Často refuse: slová nesedia na „PTO“ / „US employees“. Môže nájsť tú istú kartu cez význam.
Načo Web, evaly a CI bez GPU. Vidíš UI, citácie, Deny od Policy. Keď chceš naozaj AI, nie výstrižok vety.

Čo je stub? Nie je to LLM.

Záslepka dvoch zásuviek, nie druhý model. StubEmbeddingGenerator hashuje slová do 64 čísel. StubChatClient skopíruje vety z retrievanutých chunkov, kde sa prekrývajú slová. Porovnanie so skutočnou Ollamou je v tabuľke vyššie.

Ako by sa to volalo pri reálnych firemných dátach

Nie Assistant. Bežný tvar:

  • Knowledge — modul
  • Connectors — SharePoint, fileshare, Confluence, export z HR/Finance
  • Ingest / Indexer — narezať + embednúť + uložiť
  • Retriever / Generator / Guardrail — to, čo už máš ako Ask + Policy
  • DocumentSync — sleduje zmeny
  • AuditLog — kto sa pýtal, z čoho sa odpovedalo
  • VectorStore — dnes InMemory, neskôr pgvector (IDocumentIndex ostáva švík)

Áno, má bežať sync: zmení sa jeden súbor → len ten sa znova nareže a upsertne. Nie full reindex celej firmy a nie 12 helper metód na každú chybu.

Čo je v tomto prototipe zmenené (veľký DDD refactor nie)
  • Status: provider, model, chunky, ingest. Žiadny pull modelov, žiadny ask log v procese.
  • OllamaGateway: probe + normalizácia endpointu. Pull preč.
  • UI: tichší layout (žiadny fialový gradient / „dopamine“ CSS).
  • Assistant:VectorStore=InMemory — neskôr PgVector cez to isté IDocumentIndex. Cloud/Ollama/stub v factory ostáva.

Ingest / chunk / embed / index (skrátene)

Ingest: prečítať data/seed/policy/*.md, narezať, embednúť, uložiť — pri štarte, nie pri otázke.

Chunk: kúsok dokumentu (MediTokenChunker, ~640 tokenov), nie celý šanón.

Embed: čísla významu. Ollama = nomic-embed-text. Stub = hash slov (preto lexikálny filter v handleri).

Index: InMemoryDocumentIndex, umrie s procesom Web. Swap = IDocumentIndex.
